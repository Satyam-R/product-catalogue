# Decisions and assumptions

- **Catalogue data.** The exercise permits sample metadata. The bundled dataset keeps the demo and tests repeatable and gives each category enough entries to show top-rated and additional products. The backend owns the fixture and exposes a `ProductSource` interface for a future API or database.
- **Featured and search rules.** The home page uses five configured IDs in their selected order. Categories rank by rating, then by ID for ties, and show three top-rated items followed by the rest. Search matches a trimmed term against titles and descriptions, ignoring case. A blank search prompts the customer to enter a term. Sample prices use USD.
- **Enquiry.** Name and email are sufficient to follow up about a known product. The server supplies the product details and sales address, and uses the customer's validated email as Reply-To. In the demo, MailDev is the sales inbox. A successful response means the configured SMTP server accepted the message.
- **Scope and structure.** Data is read-only, the UI uses one responsive web layout, and enquiries are delivered synchronously to SMTP. Those choices cover the five required flows and fit the exercise time box. React and CSS own presentation, while the backend handles product rules and enquiry validation. A different mail implementation can be supplied through `EnquiryMailer`.
- **With another day.** Add automated browser coverage for the enquiry and its failure state, then add a persistent enquiry record and duplicate protection if the owner wants the app to handle real customer traffic.
